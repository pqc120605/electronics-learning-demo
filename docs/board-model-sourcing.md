# Board model source and publication status

Last reviewed: 2026-11-03. A board in the catalogue, a source archive, a 3D preview and a validated interactive model are different support levels. Do not describe a catalogue entry as an uploaded model.

Latest geometry and deviation findings are tracked in [board-model-accuracy-audit-2026-11-03.md](board-model-accuracy-audit-2026-11-03.md). That report checks the published GLBs against retained CAD/source evidence; it does not certify a physical sample.

## Raspberry Pi Pico-family J0 pin references — 2026-11-03

- The Pico, Pico W, Pico 2 and Pico 2 H board viewers expose all 40 J0 header pads in the pinout panel and as selectable 3D anchors. Selecting one reports its J0 pad number, CAD net, official pin label, documented alternate functions and a safety note. This is static reference data: it does not create wires, highlight PCB copper, trace firmware, or simulate electrical behavior.
- **Direct pad evidence:** KiCad PCB Editor CLI 10.0.7 imported the official Allegro sources `assets/boards/vendor/raspberry-pi/official-allegro/RPI-PICO-R3a-PUBLIC.brd` (SHA-256 `C9C6D1E95409B68B77501093EF42EA266D7F30025F907E4A962167E088BEDEBD`) and `rpi-picow-r3-2.brd` (SHA-256 `574C6112A3418DFF77717F87E62839F5205CF9FD1899350F4CE16610DEE731A5`). The JSON records all 40 pad centers in mm, CAD net names, source hashes, and per-STEP transforms. Pin labels/functions are sourced separately from Raspberry Pi's [Pico 2 pinout](https://datasheets.raspberrypi.com/pico/Pico-2-Pinout.pdf) and [Pico W pinout](https://datasheets.raspberrypi.com/picow/PicoW-A4-Pinout.pdf).
- **Inherited layout:** Raspberry Pi documents the common physical layout and pinout across non-wireless Pico/Pico 2 variants and separately across wireless Pico W/Pico 2 W variants in its [Pico-series documentation](https://www.raspberrypi.com/documentation/microcontrollers/pico-series.html). The available four viewer SKUs are Pico, Pico W, Pico 2 and Pico 2 H; Pico 2 and Pico 2 H use the non-wireless Pico J0 layout transformed into their own STEP axes. There was no Pico 2- or Pico 2 H-specific Allegro board in the local source set, so those anchors are not claimed as direct board-specific pad extractions.
- **Coordinate handling:** source pad positions remain recorded in millimeters; `src/data/raspberryPiPicoPinout.ts` applies the documented per-variant translation and top-surface offset, then emits GLB-world anchors in meters. The USB edge and board outline were used to check axis direction. This is a model-space alignment, not a physical measurement of the user's board.
- **Local record:** see `src/data/raspberry-pi-pico.j0-pads.json` for source hashes, all pad centers/nets, pitch and transform basis; `src/data/raspberryPiPicoPinout.ts` contains the sourced pin labels, functions and cautions. Pico W's antenna restriction remains separate from this pin lookup and no RF claim is made.

## Adafruit QT Py ESP32-C3 Rev B #5405 breakout-pin anchors — 2026-11-03

- The 14 exposed JP1/JP3 pads are selectable in the 3D viewer and pinout list. The anchors come from the exact `1X07_CASTEL` Eagle package pads, rotated by the JP1/JP3 element placements, and are included only when Eagle's `N`/`NC` pad pair shares one CAD net.
- `scripts/export-adafruit-qtpy-esp32-c3-pin-anchors.mjs` checks the source Eagle CAD and GLB SHA-256 against the checked-in inventory. It matches 35 mapped STEP meshes to Eagle element centers, derives a robust translation and axis direction, checks residual/board bounds, and places anchors on the GLB PCB top surface. Regenerate with `npm run generate:qtpy-c3-pin-anchors`.
- Pad/net labels are CAD evidence; GPIO/ADC/UART/SPI functions and power notes come separately from Adafruit's [QT Py ESP32-C3 pinout guide](https://learn.adafruit.com/adafruit-qt-py-esp32-c3-wifi-dev-board/pinouts). The selection is static lookup only: it does not expose individual MCU pins or STEMMA QT contacts, build a netlist, highlight copper, run firmware, or establish that a physical #5405 board matches the model.
- Local records: `src/data/adafruit-qtpy-esp32-c3-5405.pin-anchors.json` and `src/data/adafruitQtPyEsp32C3Pinout.ts`. The published STEP/Eagle attribution and license notices remain unchanged.

## Adafruit Feather ESP32-S3 breakout-pin anchors — 2026-11-03

- The 28 exposed JP1/JP3 pads on both PID #5323 and TFT PID #5483 can be selected in the 3D viewer or pinout list. Pad centers and CAD net labels come from the exact Eagle board files; the Eagle-to-GLB fit uses 32 inlier mesh centers for #5323 and 35 for #5483 TFT, with P95 residual 0.0007 mm. Outlier geometry centers are listed in the generated JSON and are excluded from fitting only.
- `scripts/export-adafruit-feather-esp32-s3-pin-anchors.mjs` validates source CAD/GLB hashes, package pad geometry, board bounds and transform residuals. Regenerate both anchor manifests with `npm run generate:feather-s3-pin-anchors`.
- Pin labels/functions are joined separately from each manufacturer pinout guide and the exact ESP32 Arduino core variant source. The TFT board intentionally uses its own map: e.g. #5323 SDA/SCL are GPIO3/4 and TX/RX are GPIO39/38, while #5483 TFT uses GPIO42/41 and GPIO1/2. Do not copy one variant's aliases onto the other.
- This is static header lookup only. It does not map ESP32-S3 module pads, expose a generated netlist, highlight copper, trace firmware, simulate electricity, or verify a physical board. BME280 on #5323 is a footprint reserved for a sensor, not an installed sensor according to the manufacturer guide.
- Local records: `src/data/adafruit-feather-esp32-s3-5323.pin-anchors.json`, `src/data/adafruit-feather-esp32-s3-tft-5483.pin-anchors.json`, and `src/data/adafruitFeatherEsp32S3Pinout.ts`. Source CAD/STEP notices and bundled license files remain unchanged.

The GLB files under `public/models/` include the board-reference viewers and lesson assembly models. The Seeed XIAO ESP32-C3 viewer is a KiCad PCB export with generic package meshes and a 68-item CAD footprint picker; its component details include source PCB pad numbers and assigned net names. For a CAD net whose exact name is D0–D10, the table adds the separate manufacturer pinout entry; it does not infer mappings for other nets. See the inventory JSON and `SOURCE.md` for hashes and generation inputs. The schematic has a CC BY-SA 4.0 annotation, but the KiCad archive has no standalone LICENSE file. Keep the share-alike and attribution notice; archive-specific rights remain flagged because the archive has no explicit license file. The model is educational reference, not exact manufacturer-part rendering or physical verification. The Seeed XIAO ESP32-S3 remains a separate regular-board model; Sense is a different variant. The C3 3D viewer supports selection of 14 J1/J2 header pins using anchors derived from the source PCB pad centers; the pinout list is keyboard-accessible. Pin selection does not highlight PCB copper/net or trace a runtime signal. The board catalog and lesson view show evidence status, source URL, license/attribution, revision, confidence notes and unresolved issues.

Pico defect: `convert-raspberry-pi-step-to-glb.mjs` swapped STEP Y and Z, which is a reflection, so all three GLBs were mirror images of the source CAD. Pico R3 also stood on edge because its STEP is Y-up while the others are Z-up. The script now uses a rotation per file and checks that the MCU faces +Y. `tests/component-models.test.mjs` fails if BOOTSEL leaves its upper-left position relative to the MCU. Old GLBs are kept in `assets/boards/raspberry-pi/pre-orientation-fix/`.

Browser check: Pico R3 viewed in the lesson viewer lies flat with the MCU on top. Uno, Nano, Mega, Pico W and Pico 2 were checked at file level only unless the status log says otherwise. No physical board was compared.

## Board admission checklist

Before marking a board interactive or source-verified:

1. Record exact product, PCB revision, module variant and source URL/archive checksum.
2. Read the source license and terms for derived geometry, attribution, trademarks and redistribution; keep an asset preview-only if a needed right is unclear.
3. Import the exact source without substituting a similarly named board. Record import warnings and any conversion steps.
4. Compare outline, mounting holes, component references, pad centers, package rotations, connectors, headers and populated/unpopulated states against source placement/BOM and, where possible, a physical board.
5. Confirm each interactive component’s reference and pad/net identity from CAD or schematic. Keep inferred placement explanations explicitly labeled as inference.
6. Generate both copper layers from the same source revision. Preserve net IDs, via geometry and filled zones; include source hash, units, transform and omissions.
7. Review front/back layers, boundaries and high-risk components in the target browser. Test selection, keyboard access, zoom, pan and unsupported-state handling.
8. Document a reproducible export command and update the capability registry only after review. Unsupported board/lesson mappings must fail closed.
